## 1. 本次要验证的假设

**这个推理本身没错，但它优化错了目标**——见 §5.2。

## 5. 第一性分析：为什么会这样

### 5.1 把 ΔmAP 精确拆到类别

mAP50-95 是三类 AP 的**算术平均**，每类权重相同。所以：

```
ΔmAP = (Δ损伤 + Δ暗斑 + Δ亮斑) / 3
     = (−0.055 + −0.038 + +0.030) / 3
     = −0.063 / 3 = −0.0209   ← 与实测 −0.0209 完全吻合
```

结论干净：**亮斑的确是赢的（+0.030，相对 +6.2%），但它只值 1/3 权重，抵不过损伤与暗斑的合计 −0.031。**

### 5.2 为什么「提高分辨率」的推理在亮斑上成立、在整体上失效

V5 的类别误差结构（AP50-95）：

- 亮斑 0.487、暗斑 0.533 —— 这两类已接近该类任务在本数据上的上限，剩余误差主要是定位精度
- 极片损伤 **0.236** —— 差一个数量级

而 1536 画布带来的 1.55× 放大，解决的正是「小目标检不出」这个**亮斑已经基本解决**的问题（工作点召回本来就 0.896）。它没能解决损伤类的问题，因为损伤类的瓶颈不是「斑块太小」：

| 类别 | 原生尺寸（高分辨率组中位） | ROI@1536 放大后 | 瓶颈 |
|---|---|---|---|
| 亮斑 | 16.7 × 16.7 px | 26 px | 分辨率（已解决） |
| 暗斑 | 25.1 × 25.0 px | 39 px | 分辨率（已解决） |
| 极片损伤 | **18.7 × 65.4 px** | 29 × 101 px | **细长结构的定位容差 + 上下文** |

损伤框的短边只有 18.7 px，IoU≥0.5 等价于横向误差 < 6 px；同时它是**沿电芯方向延伸的细长条**，判断「这条划痕到哪里为止」需要看到周边的极片背景。ROI 裁掉了 74.9% 的画面，恰好把这类上下文一起裁掉了。

证据（可复核）：
- 损伤 AP50 `0.587 → 0.453`，工作点 TP `41 → 32`（少 9 个），FP `23 → 36`（多 13 个）
- 暗斑 AP 也掉了 `0.533 → 0.495`，而暗斑的尺寸（25 px）本来就不缺分辨率 —— 说明损失不来自像素，来自「看得到的范围」
- 唯一位移的赢家是亮斑，它是三类里**最独立于上下文**的（孤立圆斑，就地可判）

### 5.3 增强为什么在这里没有价值

预注册时认为「ROI 提高了绝对尺度，所以付得起 mosaic 的代价」。实测：付得起，但**收益为零**。

| 从 V5.1-B 到 V5.2 唯一的变化 | 实测变化 |
|---|---|
| mosaic 1.0 + close_mosaic 10 | mAP50-95 −0.0038 |
| degrees 5 + translate 0.05 | mAP50 +0.0078 |
| erasing 0.4 | 损伤 R +0.027 |
| cls_pw 0.5 → 0 | FP/千张 +6.0 |

原因可以回到数据本身：ROI 之后图像已经是**统一视角、统一构图**的窄条，`degrees 5` 的旋转、`translate 0.05` 的平移、`mosaic` 的拼接，都在模拟「拍摄位置不固定」这种**产线上不存在的变化**（产线是固定工位）。而删掉 `erasing 0.4` 的风险（抹掉 15 px 亮斑）在 ROI 下反而变小，所以加回来也没有收益。

一句话：增强的正则化收益建立在「数据多样性不足」上，而 ROI 裁剪把多样性进一步削掉了 —— 增强补的是它自己造成的洞。

### 5.4 撤回的两条结论

| 原结论 | 撤回理由 |
|---|---|
| ROI 裁剪本身有效，+0.056 | 参照物 V5.1-A 是「全图@2112 + 关全部增强」，val box loss 2.0× train，严重过拟合。修好它得到的是「不过拟合」而不是「ROI 有效」。控制增强后 ROI 为 −0.021 |
| 净损失主要来自去掉增强 | 增强加回来只动了 −0.0038（方向还相反）。假设证伪 |

## 6. 本轮修掉的三处测量缺陷

数字要可信，先把尺子校准。本轮发现并修复：

### 6.1 缓存 JPEG 与内存裁剪不一致（影响 ~1.5 个 FP/千张）

`eval_report.py` 原先读 `.cache/eval_*_roi/images/*.jpg`（ROI 裁剪后的 q95 重编码文件），而 `sweep_workpoint.py` 是**在内存里从原图现裁**。实测同样 40 张图：两种喂法有 **24 张的框不完全相同**（多数是 ±0.01 px 的坐标抖动，个别在 conf 阈值边缘翻转）。这就是上一轮「同一工作点 127.2 vs 125.7」对不上的根因。

已统一为**内存裁剪**（也更贴近产线：产线解码上传原图后直接切片，不重编码）。修复后：

| 指标 | 修复前 | 修复后 | sweep 值 |
|---|---|---|---|
| V5.1-B FP/千张 | 127.2 | **125.7** | 125.7 ✓ |
| V5.2 FP/千张 | 130.2 | **131.7** | 131.7 ✓ |
| V5.2 组级漏检 | 51/170 = 30.0% | **49/170 = 28.8%** | 28.8% ✓ |

三份报告与三份扫描现在**逐位一致**。

### 6.2 验证管线的缩放口径（`dataset.py:319`）

`LetterBox(new_shape=(imgsz,imgsz), scaleup=False)`：验证不放大小图，而训练/推理都放大。理论上对 ROI 模型（647×991 要放大 1.55× 才到 1536）影响应当很大。

实测（`scripts/eval_scaleup.py`，只改这一处口径，其余不动）：

| 模型 | 默认口径 | 改为 scaleup=True | Δ |
|---|---|---|---|
| V5 全图@1920 | 0.4186 | 0.4078 | −0.0108（−2.6%） |
| V5.1-B ROI@1536 | 0.4015 | 0.3867 | −0.0148（−3.7%） |
| V5.2 ROI@1536 | 0.3977 | 0.3992 | +0.0015（+0.4%） |

**结论：不是系统性偏袒，量级都在 ±0.015（≈1.5σ）以内，排序不变。** 此前的担心可以排除；这条只登记为口径说明，不改历史数字（改了会与已发布报告不可比）。

### 6.3 `model.val` 与产线 `predict` 的差异

层 1（COCO mAP）走 `model.val`，层 2/3（工作点 P/R、FP、组级漏检）走 `predict`。产线只有 `predict`，所以**选型决策看层 2/3**，层 1 用于横向可比。本报告的分类别 AP 属层 1，工作点 P/R 属层 2。

## 7. 顺带修掉的两个部署侧 bug（比模型本身更要紧）

### 7.1 `_load_model_spec` 永远读不到 meta（严重）

`web/app.py` 在 `os.path.dirname(best.pt)` 即 `weights/` 下找 `_train_meta.json`，但该文件在 run 根目录（`weights/` 的上一层）。后果：**任何 ultralytics 直接产出的模型都被判为「全图@1920」**，包括 ROI 模型 —— 把 16:9 全图喂给只在 647×991 上训练的模型，输出全废且不报错。

现状（已修）：

```
V52_ROI_1536_REG/weights/best.pt   {'imgsz': 1536, 'roi': True,  'source': .../_train_meta.json'}
V51_ROI_1536/weights/best.pt       {'imgsz': 1536, 'roi': True,  'source': ...}
V51_PREPROC_1021/weights/best.pt   {'imgsz': 2112, 'roi': False, 'source': ...}
V5_GROUPED_1021_80ep/weights/best.pt {'imgsz': 1920, 'roi': False, 'source': ...}
models/启用/20261019_V4/best.pt    {'imgsz': 1920, 'roi': False, 'source': 'default'}  ← 无 meta，行为不变
```

### 7.2 V5.2 的 meta 写成 `roi: False`

`train_run.py` 的「数据集名含 ROI 就自动置位」是 12:54 才加进去的，而 V5.2 进程 12:49 就启动了 —— 运行的还是旧代码（`train.log` 里没有「推理口径」那一行可作证）。**训练本身不受影响**（数据本来就是裁好的），但 `_train_meta.json` 写错了，会让部署端按全图推。

已修：`archive_experiment.py --backfill-meta` 增加「显式 False 但数据集名含 ROI 一律纠正」，`roi_of_run` 改为数据集名优先于错误的 meta 值。现在 5 个 run 的 roi 位全部正确。

2. **损伤类定向加权或过采样**（成本 2 h/轮）：损伤只占 16.5% 的框，但吃掉 1/3 的 mAP 权重。`cls_pw` 与 `copy_paste` 无效（后者对检测是 no-op），可行的是**按类别分层采样**。
3. **若仍要走裁剪路线**：应做「带余量的裁剪」（在 ROI 外扩 20~30%），保住损伤所需的上下文，而不是纯 ROI。这是一次单因素实验，2 h 可判定。
4. **补 seed 复现**（各 2.2 h）：把 §4.2 里 0.9σ/2.2σ 的模糊地带钉死。建议只在需要拿 ROI 做最终决策时才做。
