## 0. 结论先行

| 仓库 | 采纳结论 | 一句话理由 |
|---|---|---|
| **roboflow/supervision** | ✅ **采纳（切片首选）** | 与 SAHI **检出完全一致**（逐类 TP/FP/FN 全同），但延迟只有一半（56.8 vs 112.6 ms） |
| **microsoft/onnxruntime** | ✅ **采纳（CPU 部署）** | 输出与 torch **100% 等价**（63/63 框 IoU≥0.99），CPU 推理快 **1.77×**，模型 12.9 MB |
| obss/sahi | ⚠️ 仅参考实现 | 同配置同结果但慢 2 倍；其价值在 `slicing.py` 的网格算法与 4 种合并策略，不在运行时 |

| Lightning-AI/torchmetrics | ❌ 不作生产依赖 | 与项目层1 差 **−0.016 mAP**，差异几乎全在 light 类（−0.042）；口径差大于它能提供的价值 |

**最重要的产出不是"用哪个库"，而是一条新工程规则**：
> V5 的有效尺度窗口只有 **0.75～1.0**（峰值 0.90），0.45 以下直接归零，1.2 以上掉到 30%。任何"改输入尺度"的方案（切片、ROI 放大、超分、换画布）必须先过这条窗口，否则不是精度问题，是**归零**问题。

## 3. 仓库一：obss/sahi —— 切片推理

### 3.1 推荐理由
唯一"零训练成本、直接命中小目标/长条召回"的方案；`ultralytics>=8.3.161` 与本机 8.4.146 兼容；MIT；0.12.8（2026-09-30）仍在维护。

### 3.2 可复用模块清单

| 文件 | 能拿走什么 | 本项目怎么用 |
|---|---|---|
| `sahi/slicing.py`（755 行） | `slice_image` / `get_slice_bboxes` / `SliceImageResult`：网格与重叠计算，含 `auto_slice_resolution` | 若要自研切片，直接用它的网格算法，别自己写边界 |
| `sahi/predict.py`（1123 行） | `get_sliced_prediction`：切片→批量推理→坐标还原→合并全链路 | 只做实验脚手架，不进产线 |
| `sahi/postprocess/combine.py`（480 行） | `GREEDYNMM` / `NMM` / `NMS` / `LSNMS` 四种合并 + IoU 矩阵 | 跨块框合并的参考实现 |
| `sahi/models/ultralytics.py`（310 行） | pt/onnx/openvino/ncnn/torchscript 统一适配 | **注意**：内部写死 `img[:, :, ::-1]`（假定入参 RGB） |
| `sahi/annotation.py` + `prediction.py` | `BoundingBox`/`Category`/`ObjectPrediction` 数据结构 | 统一输出格式的参考 |

### 3.3 实验方案
同一考卷、同一工作点，只换"怎么喂图"：
- **A1**：slice 960×960、overlap 0.2（6 块），每块放大到 imgsz=1920（缩放 2.0×）
- **A2**：slice 2048×1152、overlap 0.2（4 块），每块缩到 imgsz=1920（缩放 0.9375×）——**保尺度**

### 3.4 验证结果

| 配置 | 损伤 R | 暗斑 R | 亮斑 R | FP/千张 | 组漏检 | 延迟 p50 |
|---|---|---|---|---|---|---|
| 基线 1920 全图 | **0.5616** | 0.8504 | 0.8963 | **88.8** | 26.47% (45/170) | 30.7 ms |
| A1 切片 960（2.0× 放大） | 0.1644 (−39.7pt) | 0.1880 | 0.3704 | **750.0** (+661) | **78.82% (134/170)** | 200.0 ms (**6.5×**) |
| A2 切片 2048×1152（0.94×） | 0.5342 (−2.7pt) | 0.8547 | 0.9259 | 115.4 (+26.6) | **22.94% (39/170)** | 112.6 ms (3.7×) |

**A1 是灾难，A2 是 trade-off。** 差别全在"块被放大到多少倍"。

按项目预注册判据（层2/3 主判据：组漏检 −3pt 且 FP 恶化 ≤10%）：
- A2 组漏检 **−3.53pt（达标）**，FP **+29.9%（超出 10% 红线）** → **整体不通过**。
- 这不是"SAHI 不好"，是"用召回换 FP"的老路，代价被量化了：**−3.5pt 组漏检 = +26.6 FP/千张 + 2.7× 延迟**。

### 3.5 可落地建议
不直接采用 SAHI。保留两条可复用资产：`slicing.py` 的网格算法、`combine.py` 的合并策略。若将来模型具备尺度鲁棒性（多尺度训练）再回来做切片，届时直接抄这两处，不要引入整个依赖链。

## 4. 仓库二：roboflow/supervision —— 同能力、一半开销

### 4.1 推荐理由
51k Star、MIT、2026-10-22 仍在提交；`sv.InferenceSlicer` 是 SAHI 的等价能力但无 mmdet 生态包袱；`sv.Detections` 可做统一输出结构。

### 4.2 可复用模块清单

| 文件 | 能拿走什么 |
|---|---|
| `supervision/detection/tools/inference_slicer.py` | `InferenceSlicer`：`slice_wh`/`overlap_wh`/`thread_workers`/`batch_size`/`OverlapFilter.{NMS,NMM,NONE}` |
| `supervision/detection/core.py` | `Detections`：`xyxy/confidence/class_id` + `with_nms()`/`with_nmm()` |
| `supervision/detection/utils/converters.py` | `from_ultralytics`（一行接入现有权重） |
| `supervision/annotators/` | BoxAnnotator / LabelAnnotator，替代自研的 PIL 画框 |
| `supervision/metrics/` | 另一套 P/R/mAP 实现，可用于交叉验证（与 §7 的 torchmetrics 结论配合看） |

### 4.3 实验方案
与 A2 **完全相同的切片参数**（2048×1152、overlap 0.2、NMM、iou 0.5、conf 0.25），只换实现。

### 4.4 验证结果

| 实现 | 损伤 TP/FP/FN | 暗斑 TP/FP/FN | 亮斑 TP/FP/FN | FP/千张 | 组漏检 | 延迟 p50 |
|---|---|---|---|---|---|---|
| SAHI A2 | 39/21/34 | 200/37/34 | 125/20/10 | 115.4 | 22.94% | 112.6 ms |
| supervision | **39/21/34** | **200/37/34** | **125/20/10** | **115.4** | **22.94%** | **56.8 ms** |

**逐类三指标完全相同，延迟差 1.98×。** H-4 成立且强于预期：两套实现的合并语义在这个参数下等价，SAHI 的额外开销来自 Python 层的切片循环与对象封装。

### 4.5 可落地建议
**如果要做切片，用 supervision，不用 SAHI。** 省 2× 延迟且依赖更干净（无 shapely/pybboxes 链）。但仍受同一条尺度规则约束：**切片块在 imgsz 下的缩放必须落在 0.75～1.0，否则归零**。

## 5. 仓库三：microsoft/onnxruntime —— 无 GPU 机器的出路

### 5.1 推荐理由
产线有老机器/无显卡，项目已有 CPU 回退（`core/device_utils.py`）但走的是 torch CPU，慢。ORT 是零改造的加速路径，且能锁死运行时版本（便携包最怕 torch 升级）。

### 5.2 可复用模块清单

| 来源 | 能拿走什么 |
|---|---|
| Python API `onnxruntime.InferenceSession` | provider 选择（`CPUExecutionProvider`）、图优化级别、线程数控制 |
| `onnxruntime/python/tools/quantization/quantize.py` | 静态/动态 INT8（本轮未做，见 §9 待办） |
| `ultralytics` 导出链 | `YOLO.export(format='onnx', imgsz=(H,W), opset=12)`，静态 shape 12.9 MB |
| 自研 `scripts/oss_bench.py::run_ort` | 纯 numpy 解码 + 逐类 cv2 NMS（约 40 行），可直接搬进 `web/app.py` |

### 5.3 实验方案
两件事分开测，否则差异无法归因：
- **Q1 运行时是否透明**：把图 resize 到 1920×1088，**同一张数组**分别喂 ORT 与 torch（imgsz 恰好等于数组，ultralytics 不再二次缩放），按 IoU 一对一比对 60 张。
- **Q2 换链路后业务指标动多少**：全量 676 张跑层2/3。

### 5.4 验证结果

| 项 | 结果 |
|---|---|
| 一致性（60 张 / 63 框） | IoU≥0.5 匹配 63/63，**IoU≥0.99 也是 63/63**，中位 **0.9998**，一致率 **100%** |
| ORT CPU 延迟 | **99.7 ms** |
| torch CPU 延迟 | **176.1 ms** → ORT 快 **1.77×** |
| torch GPU（纯推理） | 9.6 ms（有 GPU 时仍应走 GPU） |
| 模型体积 | 12.9 MB（静态 shape，opset 12） |
| 全量指标（676 张） | 损伤 R 0.5479、FP 84.3、组漏检 25.29% (43/170) |

全量指标与基线有微小差异（FP 84.3 vs 88.8，损伤 R −1.4pt），**原因是预处理**：ORT 走纯 resize 到 1920×1088，基线走 ultralytics letterbox 到 1920×1920 + 840px padding。两者不是同一张输入，所以差异不能算到运行时头上——Q1 已经把运行时排除干净了。

### 5.5 可落地建议
1. 在 `web/app.py` 增加 `--backend ort|torch` 开关，默认仍 torch；无 CUDA 时自动优先 ORT。
2. 导出时机：模型验收后与 `_train_meta.json` 一起产出 `.onnx`，md5 一并登记（沿用现有 `weights.txt` 纪律）。
3. 注意：**ONNX 是静态 shape**，换 `--imgsz` 就要重导，必须把 `imgsz` 写进 meta 并在加载时校验，否则会出现"图按一种尺寸、模型按另一种"的静默错位（L-012 同类）。

## 6. 仓库四：cleanlab/cleanvision —— 数据集审计

### 6.1 推荐理由
Apache-2.0、纯 Python、CPU 30 秒跑完 676 张；能独立验证"冻结清单是否真的干净"，这是 P0-B 标注审计之外的另一种证据。

### 6.2 可复用模块清单

| 文件 | 能拿走什么 |
|---|---|
| `cleanvision/imagelab.py` | `Imagelab(filepaths=[...]).find_issues()/report()`，不落盘、可对任意子集跑 |
| `cleanvision/issue_managers/duplicate_issue_manager.py` | 精确 + 近重复（hash + 距离阈值） |
| `cleanvision/issue_managers/odd_size_issue_manager.py` | 尺寸异常检测 |
| `cleanvision/issue_managers/blur_issue_manager.py` 等 | 模糊/低信息量/亮度（对 CT 意义有限，见下） |

### 6.3 实验方案
对 test 676 张跑默认 9 类检查，再用清单 `md5` 列独立做跨 split 精确重复校验，最后按分辨率桶交叉统计真实 FP。

### 6.4 验证结果

| 检查项 | 命中 | 判读 |
|---|---|---|
| `near_duplicates` | **540 / 676** | **不是脏数据**。冻结清单本身就是按 cos≥0.999 做电芯分组，同电芯连拍必然是近重复 |
| `exact_duplicates` | 4 | 同 split 内完全同图（重复拍摄） |
| `odd_size` | **71** | **与"1052 系列低分辨率桶"完全对上**（71 张），独立复现了项目自己的分桶 |
| dark / light / blurry / low_information / odd_aspect_ratio / grayscale | 0 | CT 为灰度图，`grayscale` 这类"问题"对本项目无意义——**这是工具与场景的语义错配** |

独立校验冻结清单（按 md5）：

| 项 | 结果 |
|---|---|
| 跨 split 精确重复组 | **0** |
| 同 split 精确重复组 | 20 |

**结论：冻结清单在"精确重复"这一层是干净的**，与 `v5_split_manifest_stats.json` 里 `leak_problems: []` 一致。这给了清单一个第三方背书。

按分辨率桶的真实误检（用同一匹配器重算）：

| 桶 | 张数 | 预测框 | FP | FP/千张 | 精确率 |
|---|---|---|---|---|---|
| 低分辨率（1052 系列） | 71 | 47 | 7 | **98.6** | **0.851** |
| 高分辨率 | 605 | 374 | 53 | 87.6 | 0.858 |

**这条数据证伪了一个流行假设**：低分辨率桶的精确率 0.851 vs 0.858，几乎没有差别——"小图插值放大导致误检多"在 V5 全图@1920 上**不成立**。低分辨率桶的问题不是误检率，而是它只有 71 张、样本量本身不足以下结论。

### 6.5 可落地建议
- 只在"数据集体检"这个用途上引入，每季度或每次物化新数据集后跑一次，输出 `reports/audit/cleanvision_<dataset>.json`。
- **必须屏蔽 `grayscale`/`dark`/`light` 三类**，否则每次都是噪声报告。
- 不要用它做近重复判据：它的阈值是通用图像语义，和本项目的电芯分组口径（cos 0.999 + MAE 1.5）不一致。

## 7. 仓库五：torchmetrics —— 评估口径对拍（结论：不适配）

### 7.1 推荐理由
项目层2/3 是自研匹配器，层1 借 ultralytics.val，两者都在"自己人"的代码上。L-023 已经证明过静默错位能把指标全跑错。第三方实现是唯一能独立复现的尺子。

### 7.2 可复用模块清单

| 文件 | 能拿走什么 |
|---|---|
| `torchmetrics/detection/mean_ap.py` | `MeanAveragePrecision`（COCO 兼容，`class_metrics=True`） |
| `torchmetrics/detection/helpers.py` | 后端抽象（pycocotools / faster-coco-eval 可切换） |
| 依赖 | Windows 上 `pycocotools` 需 MSVC，改用纯 Python 的 `faster-coco-eval` |

### 7.3 实验方案
用同一份预测（conf=0.001，676 张，2196 框）与同一份 GT（442 框）复算 mAP，与 `reports/eval/V5_80ep_v5test.json` 的层1 对比。

### 7.4 验证结果

| 指标 | torchmetrics | 项目层1 | Δ |
|---|---|---|---|
| mAP50-95 | 0.4026 | 0.4186 | **−0.016** |
| mAP50 | 0.7958 | 0.8028 | −0.007 |
| mAP75 | 0.3873 | 0.4090 | −0.022 |
| damage AP | 0.2343 | 0.2363 | −0.002 |
| dark AP | 0.5285 | 0.5326 | −0.004 |
| **light AP** | **0.4450** | **0.4869** | **−0.042** |

**H-6 证伪。** 但归因很重要：
- damage / dark 差 0.002~0.004，**在噪声内** → AP 公式本身没有分歧。
- light 类差 0.042 → 唯一可疑点。light 是小目标、数量最多的类（135 框），对预处理差异最敏感。
- 首要解释是**预处理不同**：层1 走 `model.val`（`rect=True`，按批次内统一长宽比 letterbox），我的对拍走 `predict`（方形 1920 + 840px padding）。两者看到的不是同一张图，预测自然不同。
- 已排除 max_det 截断：实测每图最多 32 框，远低于 300 上限。

**所以这不是"项目指标算错了"，而是"两把尺子的刻度差 1.6pt"。** 这件事本身就是有用结论。

### 7.5 可落地建议
不作为生产依赖（多一个含 torch 生态的依赖对便携包是负债）。但要做**两条纪律**：
1. 任何 mAP 数字必须标注来源（`val` 口径 / `predict` 口径），否则跨工具比较就是错的——这与 `DECISIONS` D-005「层1 只用于横向比」是同一件事的延伸。
2. 若要真对拍，必须让两条链路用**同一批预测**，而不是各跑一遍模型。

## 8. 副产品：尺度窗口（本轮最硬的结论）

用 20 张含损伤图，只改 imgsz，数检出框：

**[A] 整图（2129×1198）**

| imgsz | 有效缩放 | 检出框 | 损伤框 | 延迟 |
|---|---|---|---|---|
| 640 | 0.301 | **0** | 0 | 82.9 ms |
| 960 | 0.451 | **0** | 0 | 6.9 ms |
| 1280 | 0.601 | 6 | 6 | 8.8 ms |
| 1600 | 0.752 | 12 | 12 | 12.1 ms |
| **1920** | **0.902** | **20** | **20** | 14.8 ms |
| 2112 | 0.992 | 17 | 17 | 17.6 ms |
| 2560 | 1.202 | 6 | 6 | 24.2 ms |

**[B] 960 切片单块**

| imgsz | 有效缩放 | 检出框 |
|---|---|---|
| 480 | 0.5 | 0 |
| 736 | 0.767 | 4 |
| 960 | 1.0 | 3 |
| 1280 | 1.333 | 4 |
| 1920 | 2.0 | 9 |

**读法**：模型不是"分辨率越高越好"，而是**只在 0.75～1.0 这一档有效**。这一条同时解释了三个历史现象：
- `AGENTS.md` 里"640 下几乎检不出"（0.30×→归零）
- V5.2 ROI 训练里"小图放大 10.2×"必然崩
- 切片若不控制块缩放，会把整条链路推出窗口（A1 的 750 FP/千张）

### 8.1 由它反推的实验：多尺度融合

既然 0.902 和 0.992 各有 20 / 17 个检出（不完全重叠），把两档融合可能互补。

| 方案 | 损伤 R | FP/千张 | 组漏检 |
|---|---|---|---|
| 1920 单尺度（基线） | 0.5616 | **88.8** | 26.47% |
| 2112 单尺度 | 0.4658 | 122.8 | 24.71% |
| 融合 NMS @conf .25 | 0.5753 | 110.9 | **21.76% (−4.71pt)** |
| 融合 WBF @conf .25 | **0.5890** | 147.9 | 22.35% |
| 融合 NMS @conf .35 | 0.5068 | **88.8** | 25.29% |
| 融合 NMS @conf .45 | 0.4521 | 63.6 | 27.65% |

**关键在等 FP 工作点**：conf 抬到 0.35 时 FP 正好回到 88.8，组漏检只改善 **1.18pt**，代价是损伤召回掉 **5.5pt**。→ **净收益不成立**，与"整条 PR 曲线被 V5 支配"的判断一致。

**唯一值得记住的一行**：WBF 融合把损伤召回推到 **0.5890（+2.74pt）**，这是本轮唯一改善损伤召回的配置，代价是 FP +59.1。若将来损伤召回成为唯一 KPI、FP 不再是硬约束，这条路可以重新评估。

## 10. 局限与未做完的事

1. **只有 676 张 test、73 个损伤框**：损伤召回的分辨率约 ±11pt，本轮所有损伤相关结论（−2.7pt、+2.7pt）都在噪声边缘，不能单独作为决策依据。组漏检（170 组）和 FP（676 张）才是可靠指标。
2. **没有测 INT8 量化**：ORT 静态量化需要校准集，属于下一轮；预期 CPU 再快 1.5～2×，但小目标精度损失需要单独评估。
3. **没有测 GPU 上的 TensorRT**：本机 RTX 5060 (sm_120) 需 TensorRT 10.8+，与便携包 torch 2.8 的部署链耦合，超出本轮范围。
4. **cleanvision 的 near-duplicate 540 张未做组内/组间分解**：若要拿它做泄漏证据，必须按 group 字段拆分后重算（本轮用 md5 精确重复替代，结论是跨集 0 组）。
5. **多尺度融合只试了 1920+2112**：其他组合（1600+1920、1920+2560）未扫，WBF 的权重策略也未调。
