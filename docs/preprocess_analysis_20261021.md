## 0. 一页结论

| 项 | 实测 | 判定 |
|---|---|---|
| 长宽比 | **全部横向 16:9**（AR p50 = 1.777，范围 1.777~1.814），0 张方图 | 方形画布天然浪费 |
| 当前 `imgsz=1920` 方形画布的填充率 | **56.0%**（内容只有 1920×1080） | **44% 算力烧在填充区** |
| 原生尺寸 | 只有 2 类：2129×1198（3118 张，68%）、1052×580~585（1468 张，32%） | 双峰分布 |
| 高分辨率组在 1920 下 | 缩小 **0.902**（轻微下采样） | 尚可 |
| 低分辨率组在 1920 下 | **上采样 1.825 倍** | 插值假分辨率，无信息增量 |
| 缺陷等效边长（高分辨率组，原生） | 极片损伤 37.7px / 暗斑 25.8px / **亮斑 16.8px** | 亮斑最小 |
| 低分辨率组亮斑原生边长 | **10.1px** | 已接近 stride 8 极限 |
| mosaic 后亮斑 | p50 **7.9px**，**52.6% 的框 < 8px**，98.9% < 16px | **mosaic 在杀死亮斑** |
| 缺陷对比度（缺陷内 − 周边环） | 暗斑 **−3.3**、亮斑 **+3.3** 个灰度级（8bit） | 极微弱 |
| 局部噪声 std | 暗斑 4.1、亮斑 3.7 灰度级 | 单像素 SNR < 1，靠多像素平均 |
| 可检出指数 SNR（p50） | 原图 18.6/18.7/13.4 → @1920 16.7/16.8/12.0 → **mosaic 9.3/9.3/6.7** | mosaic 让 SNR 腰斩 |
| JPEG 再编码（q90/q75） | 对比度保留率 **0.994~1.009** | **不是瓶颈**（负面结论） |
| 插值方式（当前 0.902 缩放率） | LINEAR 1.015 / AREA 1.016 / NEAREST 0.898（light） | NEAREST 有害，其余等价 |

**一句话**：真正的瓶颈不是"插值算法选错"，而是 **① 方形画布浪费 44% 算力 ② mosaic 把已经只有 16px 的亮斑压到 8px 以下 ③ 32% 的数据被上采样 1.8 倍假装高分辨率**。这三条都能在不改模型结构的前提下修掉。

> ⚠️ **先纠一处类名**：你在问题里写的是 `1=亮斑、2=暗斑`，与代码事实相反。`core/Config.py:16-19` 定义的是
> `0=damage 极片损伤`、`1=dark 暗斑`、`2=light 亮斑`。
> 本报告全部按代码口径书写：**1 = dark 暗斑，2 = light 亮斑**。读 `reports/eval/*.json` 时也按这个口径，否则会把"暗斑好、亮斑差"读反。

## 2. 实测数据

### 2.1 分辨率与长宽比（全量 4592 张）

| 原生尺寸 | 张数 | 占比 | AR |
|---|---|---|---|
| 2129×1198 | 3118 | 67.9% | 1.777 |
| 1052×582 | 953 | 20.8% | 1.808 |
| 1052×585 | 496 | 10.8% | 1.798 |
| 1052×580 | 19 | 0.4% | 1.814 |
| 2115×1183 | 6 | 0.1% | 1.788 |

- 只有 **5 种分辨率**，且全部 16:9 → 处理可以完全确定性，不需要"杂分辨率"容错逻辑。
- **0 个分组同时包含大小两种尺寸**（`preprocess_analysis_extra.json`）→ 低分辨率组**不是**高分辨率组的缩放副本，是真实的两次导出。这点很重要：意味着不能靠"去重"解决，只能分层对待。
- 通道：全部 3 通道（BGR）；边框区域灰度 std p50 = 23.5，说明**没有大片纯色黑边**，所以 1920 方形画布的填充区是"凭空多出来的"，不是和原有黑边重叠。

### 2.2 三种画布的填充率（这是省钱的关键）

| 画布 | 2129×1198 组 | 1052×582 组 | 说明 |
|---|---|---|---|
| **1920×1920（现状）** | 缩放 0.902，填充 **56.3%** | 缩放 **1.825**，填充 **55.3%** | 44% 内容区是灰 |
| 1920×1088（矩形） | 缩放 0.902，填充 **99.3%** | 缩放 1.825，填充 **97.6%** | 内容分辨率与现状**完全相同** |
| 2112×1184（矩形，原生 1:1） | 缩放 **0.988**，填充 **99.6%** | 缩放 2.008，填充 **98.7%** | 68% 数据第一次拿到近 1:1 |

算力：3.69 MP → 2.09 MP（−43%）→ 2.50 MP（−32%）。**注意第三个方案画布更小但分辨率更高**——因为不再给空白区算卷积。

### 2.3 三类缺陷的像素尺寸（按分辨率组拆开，p50）

| 类 | 组 | 框数 | 原生 px | @1920（现状） | @2112×1184（建议） |
|---|---|---|---|---|---|
| 极片损伤 damage | 高分辨率 | 358 | 37.7 | 34.0 | **37.3** |
| 极片损伤 damage | 低分辨率 | 126 | 26.9 | 49.2（插值放大） | 54.1（插值放大） |
| 暗斑 dark | 高分辨率 | 1423 | 25.8 | 23.3 | **25.5** |
| 暗斑 dark | 低分辨率 | 137 | 15.0 | 27.3（插值放大） | 30.0（插值放大） |
| **亮斑 light** | 高分辨率 | 770 | 16.8 | 15.1 | **16.6** |
| **亮斑 light** | 低分辨率 | 131 | **10.1** | 18.4（插值放大） | 20.2（插值放大） |

- 低分辨率组那几行的"变大"是**插值出来的**，真实信息量仍按原生列算。10.1px 的亮斑放大到 20.2px 只是更模糊，不会更清楚。
- 当前 1920 方形下，**亮斑只有 15.1px**（高分辨率组），这是 P3(stride 8) 的两个格子。

### 2.4 mosaic 之后（现状增强的真实代价）

| 类 | 边长 < 8px（P3 一个格子） | 边长 < 16px |
|---|---|---|
| 极片损伤 | 0.2% | 39.3% |
| 暗斑 | 15.8% | 78.1% |
| **亮斑** | **52.6%** | **98.9%** |

mosaic 把 4 张图各缩到一半线性尺寸 → 缺陷面积变 1/4。对 15.1px 的亮斑，直接掉到 7.9px，**超过一半的亮斑框落到 P3 一个特征格子以内**。

### 2.5 对比度、噪声、SNR（为什么"降分辨率"是致命的）

| 类 | 对比度 p5 / p50 / p95（灰度级） | 噪声 std p50 | SNR 原图 | SNR @1920 | SNR + mosaic |
|---|---|---|---|---|---|
| 极片损伤 | −24.0 / **−6.5** / +10.8 | 20.4 | 18.6 | 16.7 | 9.3 |
| 暗斑 | −6.1 / **−3.3** / −1.0 | 4.1 | 18.7 | 16.8 | 9.3 |
| 亮斑 | +0.1 / **+3.3** / +13.1 | 3.7 | 13.4 | 12.0 | **6.7** |

- 暗斑/亮斑的中位对比度只有 **3.2~3.3 个灰度级**（8bit 共 256 级）。单像素层面噪声与信号同量级（std 3.7~4.1），之所以还能检出，是**多像素平均把噪声压了 sqrt(N) 倍**（SNR 13~19）。
- 这解释了两件事：
  1. 为什么 640 分辨率几乎检不出（`AGENTS.md` 第 1 条实测）：直接把 N 砍掉 9 倍，SNR 掉 3 倍，低于检出线；
  2. 为什么 mosaic 有害：N 变 1/4，SNR 从 13~19 掉到 6.7~9.3。
- 极片损伤的对比度**极性是混的**（p5 是负、p95 是正），说明它既可能是暗损伤也可能是亮损伤，**不能用"亮度差"来刻画**，必须依赖纹理/边缘信息——而纹理恰恰最怕下采样。

### 2.6 插值方式的实测保留率（缩放率 0.902 下）

| 类 | NEAREST | LINEAR | AREA | CUBIC | LANCZOS4 |
|---|---|---|---|---|---|
| 暗斑 | 0.988 | 1.015 | 1.016 | 1.020 | 1.016 |
| 亮斑 | **0.898** | 0.993 | 0.984 | 0.971 | 0.971 |
| 极片损伤 | −2.111 | −0.196 | −0.258 | −0.244 | −0.239 |

**这张表要正确读，不能过度解读**：

- 在 0.902 这种轻微下采样下，**除 NEAREST 外所有核的均值对比度保留率都在 1.0 附近** → 也就是说：**"换插值算法"不是当前的主要收益来源**。这是本次分析的**负面结论**，必须写清楚，避免为了"优化"而白改一通。
- 极片损伤那一行的负数**不代表插值把对比度搞坏了**，而是该类的对比度极性混合（有正有负），比值的分母跨零导致数学上无意义。这是度量方法的局限，不是数据问题。**极片损伤无法用单一"亮度差"指标评估**。
- NEAREST 对亮斑掉 10%（0.898），且会引入块状伪影 → **任何时候都不要用 NEAREST 做缩放**。ultralytics 默认 LINEAR 是安全的。
- 需要补一句严谨性：均值对比度保留率**不反映混叠（aliasing）**。AREA 相对 LINEAR 的真正优势在抗混叠（噪声不会被采样成假纹理）。在本数据的 0.902 缩放率下差异很小，但如果未来做大比例下采样（例如统一到 1052 宽），**必须用 INTER_AREA**。

### 2.7 被排除的怀疑项（负面结论，同样重要）

| 怀疑 | 实测 | 结论 |
|---|---|---|
| JPEG 压缩吃掉了微弱缺陷 | 再编码 q90 保留 0.996~1.004，q75 保留 0.994~1.009 | **不是问题**，不用改存储格式 |
| 图像有大片纯色黑边，方形画布其实没浪费 | 边框灰度 std p50 = 23.5 | **没有黑边**，44% 确实是纯浪费 |
| 两种分辨率是同一张图的两次导出（伪重复） | 0 个分组同时含两种尺寸 | **不是伪重复**，是真两份数据 |
| 图像是灰度却存成 3 通道，白算 3 倍 | 3 通道但通道值不完全相等（JPEG 色度量化残留） | 有色度残留，**不建议改单通道**（收益小、风险大） |

## 5. 增强策略调整建议

| 参数 | 现状 | 建议 | 理由（数据支撑） |
|---|---|---|---|
| `mosaic` | 1.0 | **0.0**（先验证）或 **0.3** | 亮斑 52.6% 的框 mosaic 后 <8px；SNR 13.4→6.7 |
| `close_mosaic` | 10 | 保持 10（若 mosaic>0） | 收尾阶段关掉 mosaic 已是好习惯 |
| `degrees` | 5.0 | **0.0**（或改 90° 倍数旋转） | 任意角旋转必然重采样；本数据对比度仅 3 个灰度级，重采样有损。90° 旋转无插值、无损 |
| `translate` | 0.05 | 0.05~0.1 | 补 mosaic 关掉后的位置多样性 |
| `scale` | 0.05 | 0.05（不要加大） | 缩小 aug 等于降分辨率，会砍 SNR |
| `hsv_v` | 0.1 | 0.05~0.1 | 缺陷靠 3 灰度级差，亮度扰动是噪声源；但完全不扰动会让模型怕曝光变化，保持小值 |
| `hsv_h/s` | 0 | 0 | 近灰度图，无意义 |
| `fliplr` | 0.5 | 0.5 | 缺陷无方向性，安全 |
| `copy_paste` | 0 | **0.3（仅对 damage 试）** | 极片损伤只有 484 框且 AP 最低（0.236），是最缺样本的类 |
| `mixup` | 0 | 0 | 叠加会稀释微弱亮斑，保持关闭 |
| `erasing` | 0.4 | **0.0~0.1** | ultralytics 默认随机擦除；对 3 灰度级缺陷可能直接抹掉目标 |

> `erasing` 这一条要注意：ultralytics 8.4 默认 `erasing=0.4`（随机擦除），本项目没有显式关闭。建议显式设 `erasing=0`，因为擦除块可能正好盖住 15px 的亮斑，等价于制造错标。

## 6. 落地步骤

### 阶段 1：零风险，立刻可做（不重训）

```powershell
# 1) 画布自检：确认各尺寸在各画布下的缩放率/填充率
runtime\python.exe core\preprocess.py --selfcheck

# 2) 推理端换矩形画布（模型不用重训，检测结果等价）
#    web\app.py:61
#    INFER_SIZE = (1088, 1920)    # 原 1920
```

实测依据：同一张图在 `imgsz=1920` 与 `imgsz=(1088,1920)` 下，**检测框坐标一致（容差 2px）、框数相同**；画布 3.69 → 2.09 MP。
单图延迟在 GPU 被训练占用时测得 27.4 ms → 24.9 ms（−9%）；**算力是真降 43%，但小模型 + 单图推理是开销主导，所以延迟收益要等 GPU 空闲时复测**。

### 阶段 2：下一次训练用方案 C（需重训）

```powershell
runtime\python.exe scripts\train_run.py `
    --data datasets_v5\CT_DATASET_V5_GROUPED\data.yaml `
    --model models\pretrained\yolov8n.pt `
    --imgsz 1184x2112 `
    --epochs 120 --patience 30 --lr0 0.001 `
    --name V6_NATIVE2112
```

`--imgsz` 已支持 `1920`（方形）/ `1088x1920` / `1184x2112` / `auto`，内部由 `core/preprocess.py::resolve_imgsz` 解析并保证是 32 的倍数。
**训练与推理必须同改**：`web/app.py` 的 `INFER_SIZE` 也要设成 `(1184, 2112)`，否则重演"1920 训练 / 640 推理"的事故。

### 阶段 3：分层评估（这一步不做，前两步等于没做）

当前 `eval_report.py` 把所有 test 图混在一起算。建议加一个 `--group-by resolution`，分别报高/低分辨率组的三层指标，用来回答：

- 低分辨率组（32%）是不是明显更差？
- 如果是，是继续把它留在训练集里拖后腿，还是让产线重新导出全分辨率？

这属于**数据决策**，需要你拍；我不擅自改划分。

| 方案 C：mAP 提升 | **预期，待验证** | 小目标类 AP50-95 +2~5 pt 量级；无依据的部分不写 |
| 关 mosaic：小目标 AP | **预期，待验证** | +2~4 pt，大目标可能略降 |
| copy_paste：极片损伤 AP | **预期，待验证** | 提升方向明确，幅度无法先验给出 |
| 插值换 AREA | **已实测** | 当前缩放率下 ≈ 无差异（保留率 1.0）；大比例下采样时才显著 |

**必须说清楚**：除了画布与分辨率这两项是"几何上确定的"，其余精度收益都是**待验证的假设**。验证方法只有一个：用同一份冻结 test（清单 md5 必须一致）对比，别用 val 吹。

## 8. 避坑清单

1. **`imgsz` 元组顺序是 `(h, w)`**，写反了不会报错，只会把图拉变形。用 `resolve_imgsz()` 而不是手写。
2. **训练与推理必须同分辨率**（`AGENTS.md` 第 1 条踩过的坑）。改 `train_run.py` 就必须同步改 `web/app.py::INFER_SIZE`。
3. **画布 h/w 必须能被 32 整除**，否则 ultralytics 自动向上取整，你的"省算力"就白算。
4. **不要因为对比度低就上 CLAHE**：噪声 std 3.7~4.1 与对比度 3.2 同量级，CLAHE 会把噪声一起放大，SNR 反而下降。若一定要试，`clipLimit≤1.5`、`tileGridSize=(8,8)`，且**训练与推理必须用同一套参数**，并用冻结 test 验证，不涨就撤。
5. **不要为了省算力把 imgsz 降到 1280 以下**：亮斑原生只有 15~17px，1280 宽下会掉到约 10px，重演 640 的失败。
6. **不要指望 2112 改善低分辨率组**：那 32% 的图原生就是 1052 宽，放大到 2112 只是 2 倍插值，信息量不变。
7. **不要在低分辨率组上做单图锐化/超分后混入训练**：会人为制造"两种清晰度分布"，且推理时现场图没有超分，训练-部署不一致。
8. **mosaic 关掉后要补 `translate`/`scale`**：否则位置与尺度多样性下降，大目标可能退化。
9. **改完必须用同一份清单 md5 的冻结 test 复评**（`reports/eval/compare.md` 会校验），否则数字不可比。
10. **低分辨率组的指标要单独报**，混在一起会被 Simpson 悖论误导（两组占比 68:32，混合中位数会落在两峰之间）。
