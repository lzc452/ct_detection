## 3. 数据、标注与电芯机理

### 3.1 [P0/A] 真实电芯溯源只覆盖4.12%，无法证明“同电芯不跨集”

reports/splits/v5_split_manifest_stats.json：4592 张中仅189张可恢复 cell_id；1284个近重复/溯源合并组不等于1284颗独立电芯。train/val/test 已知真实电芯数为48/13/10；test 的26张有电芯号，其余650张没有。core/dataset_split.py:163-201、221-283 的回退分组能阻止定义内的近重复，却不能识别同颗电芯的不同层位、不同视角、不同重建与不同导出尺寸。247-248 行直接跳过不同尺寸的近重复判定，也不能证明跨尺寸来源独立。

历史泄漏确实严重：旧V4验证集535/642有像素近重复（83.33%，stats文件）；F-003的635/676“93.9%”主要依据余弦近似，不能把余弦命中全部当作字节相同或直接证明训练覆盖。新分组是明显进步，但 D-002 中的“同电芯不跨集”仍是超过现有溯源证据的保证。

落地：新增不可逆匿名 cell_uid、scan_uid、slice_z/序号、view、导出批次、设备与重建版本；把同电芯及其所有派生图先聚合，再做group split；未知来源单列，不对其宣称电芯独立。保留现有test为历史开发基准，新建从未参与调参的时间/批次外部验收集。

### 3.2 [P0/A] 分辨率/来源分布的跨集偏移很大

| split | 图数 | 低分辨率图数/占比 | 损伤/暗斑/亮斑框 | 空标注图 |
|---|---:|---|---|---:|
| train | 3195 | 1013 / 31.71% | 338 / 1092 / 630 | 1337 |
| val | 721 | 384 / 53.26% | 73 / 234 / 136 | 312 |
| test | 676 | 71 / 10.50% | 73 / 234 / 135 | 287 |

core/dataset_split.py:287-344 的贪心目标仅含三类框数与负样本数，没有设备/分辨率/缺陷形态分布。验证选best的环境与最终test差别很大；F-016也显示损伤长边train中位59px、test102px（引用既有统计，未再次全量读取标签）。

落地：在真实电芯隔离约束下做多标签分层（分辨率、设备、批次、损伤短边/长边/长宽比）；不要为追求分数打散电芯。分别报桶内结果与按真实产线占比加权的总体结果。71张低分辨率test只能支持探索，不能据此选一个独立生产分支。

### 3.3 [P0/A+H] 类别是视觉表型，尚未成为可审计的工艺判废定义

Config 的0=损伤、1=暗斑、2=亮斑映射一致；但“亮/暗”只描述相对灰度，不能自动等同于金属异物/孔洞/分层或安全风险。“损伤”也可能混合裂纹、褶皱、极片边缘形变与成像伪影。当前样本是含UI和多个视图的8bit导出图，单凭检测框无法验证物理成因。

电芯开发侧需把**可见表型 → 候选物理成因 → 复核手段 → 工艺处置等级**分开：为每类提供清晰/边界模糊/伪影/不可判案例；定义极片、隔膜、极耳与边缘位置条件、最小物理尺寸、贯穿连续层数及可疑项处理。亮暗极性受窗宽窗位、重建与结构叠加影响；需要扫描/重建信息和相邻层复核，不能从一张灰度截图判定材料成分或短路风险。这是工程推断与待补资料，不是已证实的样本误标。

若有原始切片，应优先保留原始位深、标定pixel/voxel spacing及统一窗宽窗位；若只有JPG，则明确这是“固定导出协议下的2D视觉检出”，不能宣称三维物理缺陷定量。产线采集规范至少记录机型、倍率、kV/电流/曝光、重建核与降噪、位深/窗口、层间距和视图。

与电池XCT工作流中将结构分割、空间标定与可解释几何质量量化分开的做法一致，参见研究方法 [battery_xct_workflows](https://doi.org/10.1016/j.mex.2026.103856)。该研究针对圆柱电芯，不能直接移植其判废阈值到本项目。

### 3.4 [P1/A] 标注审计尚不能可靠区分“未做”与“确认为无目标”

scripts/audit_sample.py:383-403、406-418 对缺失目录/文件、JSON解析失败均返回空；437-480把它归为onlyA/onlyB/none。故漏交文件可能被解释成存在性分歧。459-466在A/B多框中挑最大IoU，不限制类别或目标关联；可能挑到双方都画的旁边结构而高估一致性。最终Gate只看双方有框子集的IoU中位，不能替代提交完整性、存在性与类别一致性校验。

落地：先做audit_id提交完整性校验，区分missing/invalid/reviewed_empty；目标关联须明确、同类一对一，并报未匹配项；加入无缺陷、伪影和难负样本，避免只看以旧框为中心的提示性视野。双人盲标与工艺专家裁决属于**人力关闭**，AI不能充当两名独立专家后宣称完成。

### 3.5 [P1/A] 高置信收割会强化现有模型已会的样本

scripts/harvest.py:12-16、31、69-83 固定V4、记录>=0.30、主要导出损伤>=0.7。适合收集“模型很像损伤”的候选，但系统性漏过低置信真损伤与完全无候选的漏检。增加这类数据不会自动增加困难覆盖。

落地：将采样预算拆为随机电芯/批次、低置信或模型分歧、误报难负样本、已确认漏检；保留抽样概率与来源，所有样本按电芯入库，验证/外部验收数据不回流训练。先建立独立抽检，再谈主动学习收益。

## 4. 模型、超参与增强的关键复核

### 4.1 [P0/A] “增强无正收益”的对照不是单因素

本次按真实args.yaml重算，忽略name/save_dir/project：

| 对照 | 实际变化 |
|---|---|
| V5 → V5.1-A | close_mosaic、cls_pw、degrees、erasing、imgsz、mosaic、scale、translate，共8项 |
| V5.1-A → V5.1-B | data、imgsz、scale，共3项 |
| V5.1-B → V5.2 | close_mosaic、cls_pw、degrees、erasing、mosaic、translate，共6项 |
| V5 → V5.2 | data与imgsz；且data中隐含裁剪、上下文、插值倍率和JPEG重编码变化 |
| V5.2 → V5.3 | data；model路径斜杠表示不同，须按解析后文件/哈希消除伪差异 |

尤其 V5.1-B 的 cls_pw=0.5，V5.2=0。该参数在当前安装库 utils/loss.py:360-362、439-440实际进入类别加权；它不是无效配置。F-005、L-011不能据此声称增强被单独否定；0.0038的mAP差在单seed下也不能推出无收益。V5与V5.2可以比较“两个完整方案”，不能将效果全部归于裁剪本身。

建议：保留历史观测，撤回过强因果解释。实验以有效干预为单位，明确控制项、允许的派生项（路径/画布/自动batch）、种子和训练预算。探索允许设计好的小型析因实验，正式确认再做单因素与重复seed；“任意YAML差异超过1项禁止”会把同文件路径写法差异当干预，反而忽视data内部变更。

### 4.2 [P0/A] erasing 没进入检测增强；Mosaic 必然缩半是错误模型

已安装 ultralytics=8.4.146。data/augment.py:2773-2854 的 v8_transforms 无 erasing、auto_augment；后两者出现在classify_augmentations。scripts/train_run.py:204-205“随机擦除损害15px亮斑”的说明与检测执行链不符。实际默认Albumentations是可选依赖；当前环境未安装，构造器存在不等于已应用模糊/CLAHE。官方也说明增强受任务和可选包影响：[YOLO数据增强](https://docs.ultralytics.com/guides/yolo-data-augmentation)。

scripts/analyze_preprocess.py:173-174 直接把所有框线性尺寸除2，继而推得“52.6%亮斑<8px”“Mosaic杀死亮斑”。安装库实际先把各图长边缩放到imgsz，拼到2imgsz画布，再按RandomPerspective矩阵裁到imgsz；其缩放范围由scale决定，并不必然0.5。合成16x16目标走真实Mosaic+恒等仿射后仍为16x16（evidence.mosaic），足以否定“必然缩半”；不能据此反过来说Mosaic一定有益。正确诊断是记录真实train_batch中每类框的输入像素分布、被裁比例及局部对比度，再做mosaic单项对照。

当前scale=0.05只在0.95~1.05间扰动；对大幅尺寸差异的覆盖有限。几何增强、亮度/噪声增强要按实际采集变化标定；固定工位仍可能有窗口/重建/曝光与结构变化，不能用“固定角度”推导“全部增强无用”。

### 4.3 [P0/A] “val 不放大小图”的归因忽略了前置 load_image

runtime/Lib/site-packages/ultralytics/data/base.py:268-279 先执行 imgsz/max(h,w)，包括上采样；dataset.py:319 的LetterBox(scaleup=False)是第二步。6张精确抽样的12种输入中，LetterBox前低分辨率全图已从585x1052变为1068x1920（1.826倍），ROI从484x319变为1536x1013（3.174倍）；后续scaleup False/True输出逐像素相同。

因此 L-014、D-007背景及scripts/eval_scaleup.py:10-21所说“ROI卡在1.0倍”不成立。旧val_scaleup.json里的数值可保留为历史观测，但不能再把差值解释为修复该机制；还需查rect批形状、缓存、运行版本与实验配置等混杂。**不修改runtime**。

同样，imgsz参数是int，不代表预测张量总是方形。predict默认rect会在同形batch使用最小stride padding，混合原始尺寸的batch可能退回整方形；官方有明确说明：[预测参数](https://docs.ultralytics.com/modes/predict)。core/preprocess.py:8、124和ROI文件头据画布面积直接宣称固定算力节省，混淆训练方形与生产实际张量。应记录preprocess后的BCHW、batch构成和时延再比较。

### 4.4 [P1/A+H] YOLOv8n 的真实结构约束与建议路线

安装库cfg/models/v8/yolov8.yaml为P3/8、P4/16、P5/32输出，没有P2/4。历史高分辨率亮斑等效边长约16.8px，1920下约15px，P3上约两个单元；长细损伤则更受短边、纹理连续性、上下文和框定义制约。stride不是硬检出下限：不能把“低于8px”解释为数学上无法检出。

先把类别任务拆清：亮暗斑适合局部目标；损伤可能需要线/区域形态表达。只有在人工一致性与全图错误分析表明AABB框难以稳定表达时，才验证分割/中心线或OBB；不能为了mAP改框定义并悄悄沿用旧test。

可落地的模型对照顺序：现有n基线 → 同输入/预算的s容量探针 → 若漏检集中在极小目标再做P2头 → 若全局结构是主因再做带上下文的局部第二阶段。s并不必然比n更准；P2增加特征图/候选密度，可能变慢且增误报，必须一起测FP和P95时延。

不优先堆注意力模块、超分或换整代YOLO；它们现在既不能补回源数据缺失，也会增加归因负担。生成式超分可能生成结构假细节，缺少原生高分辨率真值时不能作为缺陷证据。

### 4.5 [P1/A] 训练入口与归档仍有未封住的契约

- scripts/train.py:89-99 默认1280，而生产默认1920；该入口未产出完整推理meta，也未走train_run的自动归档。find_datasets只扫描旧datasets，README默认工作流还指向旧按图划分构建器。当前规范不能保证用户沿推荐入口复现V5。
- train_run.py:209接收cutmix，但291-312未传给model.train，326却记入“请求超参”；改变该选项会形成无效实验。
- train_run.py:263预算run目录，Ultralytics在重名时可自动改实际save_dir，314、360与归档仍用原路径。应使用model.trainer.save_dir、best，并在启动前写元信息、结束后补状态。
- 训练异常没有包住全程的finally；meta在训练结束才写，异常或中途取权重时规格缺失。预注册、preflight、配置diff都靠人工，入口没有执行gate。
- batch=0.75是显存比例，不是实际batch；不同尺寸可能改变batch/累积步数与训练动力学。元信息应记录实际batch、有效batch、优化器分组、步数、数据版本与源码/库版本哈希。
- “resume120”由resume-from best启动新optimizer（train_run.py:184-185、227-228），不等于恢复last.pt的optimizer/scheduler继续训练。需要分别命名为微调与真resume。
- best.pt按验证fitness选出，并不保证是损伤召回/生产误报约束下最优epoch；应只在val上预定义候选epoch规则，最终外部test一次确认。

## 5. 评测与统计问题

### 5.1 [P0/A] 工作点匹配两份实现不同，存在可复现的计数差异

eval_report.py:240-250按置信度遍历预测后，匹配**第一个**过IoU阈值的GT；sweep_workpoint.py:134-145找**最大IoU**未匹配GT，且依赖输出原有顺序。两者不是“共用同一实现”。

合成GT=[0,0,10,10]和[4,0,14,10]，高低置信预测依次=[2,0,14,10]、[0,0,10,10]，阈值0.5：先遇先配得1TP，最大IoU得2TP。已复现于evidence.matching。应抽出唯一的同类、conf排序、最大IoU一对一实现并同时测试两入口。**未重新计分前不能声称历史FP或排序已变化。**

### 5.2 [P0/A] “组级漏检”不是电芯漏放，FP框率不是过杀率

eval_report.py:189、251-254、293-309及sweep:151-156定义“组内任一GT漏掉即组漏检”。一个电芯有10处标注、检出9处仍记漏检；而只要检出一处就剔除电芯的流程中，它并没有漏放。

应并列保留：框级漏检、每组缺陷覆盖不全率、真实NG电芯完全未报警率、真实OK电芯被报警率/人工复核负荷。没有完整cell_uid和OK电芯标定不能计算后两项。88.8 FP框/千图不能换算成8.88%过杀率，多个FP可来自同一图/同一颗电芯，正样本定位偏差也会同时产生FP与FN。

### 5.3 [P1/A] 反复看同一test造成适应性过拟合；标注未冻结

sweep_workpoint默认test；FINDINGS与V6方案用test反复诊断并决定下一轮ROI边界、余量与阈值。该集可以保留为版本比较基准，但不能继续称从未参与决策的独立test。core/roi.py:18、67明确ROI包络来自全冻结清单2945框，包含test，已产生预处理参数的标签信息泄漏。

verify_split.py:44-56只校验图片MD5；manifest没有标签内容哈希。原JSON一旦变更，旧“冻结test”会悄悄换题，prepare_eval_dataset又只按图片数量复用旧标签缓存。落地：冻结image+label哈希、变换与匹配版本；阈值/ROI/架构只在train/val开发；按时间和新电芯留外部holdout。使用旧test做探查要如实标为开发后评测。

### 5.4 [P1/A] ROI评测缓存和输入规格不完整

prepare_eval_dataset:50、54-58 缓存键只有tag和roi布尔位，未包含roi_k、边界、manifest/标签hash、JPEG质量；换k但沿用tag且图片数相同，会在layer1继续用旧图/旧标签，layer2用新内存裁图，导致同份报告内部口径分叉。359-363的meta读取又静默回退k=0。layers23与sweep忽略丢框计数；异常标签可能作为负样本，掩盖错误。

### 5.5 [P1/A+B] 统计显著性与“能力天花板”解释不足

历史损伤41/73和32/73相差9框；Wilson独立比例95%区间大致分别为0.45~0.67、0.33~0.55，且同组相关性可能进一步扩大不确定性。两模型是在同一批图上评测，应使用组级配对bootstrap或配对检验，不能拿独立框近似误差条宣布“确定更差”。FP 60→89、组覆盖不全45→49支持保守选型，但不是总体因果机制或统计显著性的证明。

F-014把归一化混淆矩阵0.49称AP天花板，量纲不成立；混淆矩阵是固定置信度/匹配阈值的召回/混淆，不是AP。在当前安装库，DetectionValidator.__init__把conf=None时的混淆门槛设为0.25，训练args.conf为null；保存的训练混淆矩阵不能自动称为conf=0.001。即便显式低阈值，也受NMS、max_det、匹配规则与类别混淆影响，不能当模型能力上限。应直接保存逐图预测并扫阈值/IoU，拆分真无候选、定位偏差、分类错、低置信度与标签争议。

不要从单次train/val loss比值给出过拟合的充分判定；增强、正负构成、加载方式和损失归一化都会影响它。正常对照里观察到正收益，也不能仅因对照被称为“有病”就断言干预无效；因果主张需要更严格的控制对照。

## 6. 生产鲁棒性、速度与工程规范

### 6.1 [P0/A] 模型与规格全局可变，切换时可能错配

web/app.py:177-197按全局current_model_id取规格，而infer_one接收的model是另一个时刻的引用；切模型可发生在两者读取之间。load_model:269-284又分开替换全局引用。后台任务1600-1605对model与spec也非原子快照。core/roi.py:106-141的模块全局k在多个线程间共享，D-009“同进程多k才需重构”的触发条件已由Flask threaded=True、扫描/视频线程和切换路由满足。

落地：用不可变ModelBundle(model, model_hash, preprocess_spec)原子切换；每个任务持有完整快照，裁剪函数读bundle中的规格。单GPU优先单推理队列，入队时绑定bundle；升级/切换在队列安全边界执行。即使Ultralytics某处有内部锁，也不能保护项目外部的model/spec/k错配。参考[官方线程安全推理指南](https://docs.ultralytics.com/guides/yolo-thread-safe-inference)。

### 6.2 [P0/A] ROI布局异常仍可变成“未检出/正常”

core/roi.py:191-196说无效ROI必须报警，Web:192-197及1633-1636却仅打印最多5次警告后继续推理；空框随后记STATUS_OK_CLEAN。灰度std>=20也无法证明电芯位于正确视野，文字/其它结构可轻易通过。这是鲁棒性与业务语义缺陷。

落地：布局/图像质量失败进入needs_review或failed，计入失败分母而非OK；检测视野/电芯结构位置与尺寸的轻量一致性校验，按设备版本配置；低质量/未知协议样本禁止自动放行。需要业务判定具体复核流，代码状态与展示可先用合成异常图验证。

### 6.3 [P1/A] 同是numpy输入，Web RGB与评测OpenCV BGR不同

web/app.py:651-652用PIL转RGB再交给模型；路径读取1409起也返回RGB；Ultralytics对numpy按BGR解释，官方明确说明。当前若图片三通道严格相等，该错误被掩盖；UI彩字或未来彩色导出会受影响。统一BGR作为输入契约，并用非灰度合成图验证上传、路径、视频、eval像素一致，禁止只看灰度图测试。

### 6.4 [P0/A] Web的FP16实际上未开启；速度结论还混合了val吞吐与生产时延

**直接影响速度的确定缺陷**：core/device_utils.py:16、30在GPU可用时返回整数0，而web/app.py:66判断str(DEVICE).startswith('cuda')。str(0)为'0'，所以USE_FP16为False，即便RTX5060可用仍按FP32推理。审计工具从Web AST提取原表达式、模拟CUDA可用时执行，DEVICE=0得到False，DEVICE='cuda:0'才为True（evidence.device）。已有test_fp16的离线收益不能证明Web用了FP16。先统一设备值类型或显式按设备0判断，再用真实Web路由确认实际网络dtype与精度/时延回归；这是比缩小imgsz更直接的速度修复。

13.4ms/10.4ms来自layer1的r.speed加总，并非单张HTTP从收图到返回、更非电芯整套扫描节拍。eval_report层23以chunk32运行，Web固定batch16；同形/混形改变rect padding，影响实际FLOPs与排队时延。web:664-667把画图并入infer计时；711总时延还包含保存与save_state；各接口对“推理”的边界不同。

落地：单独报解码、裁剪、H2D、网络、NMS、画图/编码、落盘、排队与总耗时的P50/P95/P99，固定硬件/精度/batch/张量形状与预热，CUDA用正确同步计时。同时报图/秒与电芯/秒、峰值显存、失败率。先优化同形分桶和按需画图/异步写盘，再测固定形状FP16 ONNX/TensorRT；INT8必须做罕见微弱缺陷的校准与召回回归，不能只看速度。

这些后端比较不需要先把准确率差的模型上线。设备回退CPU时batch16和1920也不一定满足节拍，需独立资源配置与背压，而非静默换设备后沿用GPU期望。
