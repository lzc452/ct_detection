## 工程

### L-001 ultralytics 的日志抓不全，训练日志只剩进度条
- **标签**：工程
- **现象**：`train.log` 里只有进度条刷屏，`optimizer` / `AutoBatch` / 每轮指标全丢，事后无法复盘超参是否真的生效
- **根因**：ultralytics 的 `LOGGER` 在 **import 时就把 handler 绑到了当时的 `sys.stderr`**。之后再重定向 `sys.stdout/stderr` 对 LOGGER 无效
- **解法**：`scripts/train_run.py` 里的 `_Tee` 类不影响 LOGGER，必须**额外挂一个 `logging.FileHandler`** 到 `ultralytics.LOGGER`；控制台转录缺失的部分用 `results.csv` 逐轮回放补（`rebuild_epoch_log`）
- **证据**：`scripts/train_run.py` 的 `_Tee` / `rebuild_epoch_log`
- **首次**：2026-10-21

### L-002 Windows 下日志文件删不掉、改名失败
- **标签**：工程
- **现象**：训练结束后对 `train.log` 做任何写操作都报 `PermissionError`
- **根因**：`FileHandler` 的句柄没关，Windows 不允许删除/移动仍被打开的文件（Linux 允许）
- **解法**：结束时**先把 `sys.stdout/stderr` 复原，再 `logf.close()`**，顺序不能反
- **证据**：`scripts/train_run.py` 的收尾段
- **首次**：2026-10-21

### L-003 训练脚本改完，正在跑的进程用的还是旧代码
- **标签**：工程
- **现象**：`_train_meta.json` 里 `roi` 写成 `False`，但数据集明明是 ROI 裁剪的。查明脚本里"数据集名含 ROI 就自动置位"是 12:54 加的，进程 12:49 就启动了
- **根因**：Python 进程启动时已加载旧模块，磁盘上的改动对运行中的进程无效
- **解法**：① 长训练启动前先做一次 dry-run 打印生效配置；② 对已产出但 meta 错了的 run，用 `archive_experiment.py --backfill-meta` 幂等回填，并让 `roi_of_run()` **以数据集名为准，meta 为辅**
- **证据**：`experiments/V52_ROI_1536_REG/00_meta.json` 的修正记录
- **首次**：2026-10-22

### L-004 补丁 ultralytics 的 LetterBox 时，动态子类无法跨进程传递
- **标签**：工程
- **现象**：`eval_scaleup.py` 改完 6 秒就退出，无报错，指标是空的
- **根因**：Windows 用 spawn 起 DataLoader worker，定义在函数内的子类**无法 pickle**
- **解法**：不要新建子类。保存原 `__init__` 引用后**只替换 `LetterBox.__init__`**（见 L-005 的还原坑）
- **证据**：`scripts/eval_scaleup.py`
- **首次**：2026-10-22

### L-005 在 finally 里"还原"打补丁的类，会把类覆盖成函数
- **标签**：工程
- **现象**：补丁脚本跑完后，同进程后续所有校验的 `LetterBox(...)` 调用全部炸
- **根因**：写成 `ud.LetterBox = orig`，而 `orig` 存的是 `LetterBox.__init__` 这个**函数**，不是类
- **解法**：只还原 `__init__`：`_ORIG = [ud.LetterBox.__init__]`，`finally` 里 `ud.LetterBox.__init__ = _ORIG[0]`
- **证据**：`scripts/eval_scaleup.py`
- **首次**：2026-10-22

## 数据

### L-006 同一条归一化 ROI 边界，在两种原生分辨率上插值倍率差 4.3 倍
- **标签**：数据
- **现象**：低分辨率组（71 张）FP 从 98.6 涨到 197.2，高分辨率组从 87.6 到 125.6
- **根因**：ROI 用**归一化坐标**（x 0.3209~0.6248），所以裁出来的像素尺寸随原生分辨率线性变化：
  - 2129×1198 → ROI 647×991，撑到 1536 画布 **面积放大 2.40×**
  - 1052×582 → ROI **319×481**，撑到 1536 画布 **面积放大 10.20×**
  - 同一条裁剪规则，对小图相当于插值 10 倍，多出来的全是假细节
- **解法**：预处理按原生分辨率**分桶**，而不是一套参数走全场。小图要么用更小画布（不放大），要么先超分再裁
- **证据**：`reports/eval/by_resolution.json`；`docs/v52_why_worse_20261022.md` 原因 3
- **首次**：2026-10-22 · `V52_ROI_1536_REG`

### L-007 ROI 边界只保证"框在画面内"，不保证"框的上下文在画面内"
- **标签**：数据
- **现象**：ROI 变换的 `n_dropped` 恒为 0（看起来完美），但损伤类召回仍然崩了
- **根因**：`labelme_boxes_in_roi` 的判据是"框完整落在 ROI 内"，这是**包含式约束**。而"能不能判断这条划痕到哪里结束"需要的是**距离约束**：框周边至少要看得到 N 个像素
- 实测：损伤框到 ROI 边界距离 < 自身半长边的比例 **9.7%**；暗斑 0.1%、亮斑 0%
- **解法**：边界定义从 `包络 + 2.5% 固定余量` 改成 `margin = max(k · 框长边, c)`，k 取 1.0~1.5
- **证据**：`core/roi.py`；贴边统计见 `docs/v52_why_worse_20261022.md` 原因 1
- **首次**：2026-10-22

### L-019 审计裁剪图别用方形视野，也别放大到看得清
- **标签**：数据
- **现象**：首版用「框中心 + 4x 方形视野」：18x275px 的划痕在 1098px 画布上只占 1.6% 宽，contact sheet 上根本看不出目标，等于在测眼力而不是测标注一致性
- **根因**：损伤长宽比中位 4.13、p90 17.05，方形视野必然把细长目标压成一条线；而按短边放大到「看得清」又会改变误差的物理量纲——放大 m 倍，标注员手抖折算回原图只剩 1/m，IoU 被系统性抬高，审计变成自我安慰
- **解法**：视野各向异性（宽=短边x8 clamp 120~560，高=长边x1.6 clamp 150~900），框在视野里稳定占宽 8~13%、高 60~70%；放大倍数固定 2x 对齐模型实际输入（V5 0.90x / V5.2 1.55x），并在结论里声明为一致性的乐观上界
- **证据**：A001 18x275px：方形 1098 画布占比 1.6% 宽；改后视野 140x439、框占宽 12.5%，肉眼可辨边界
- **首次**：2026-10-23


## 训练

### L-008 一次改 5 个变量，事后无法归因
- **标签**：训练
- **现象**：V5.1-A（全图@2112 + 关全部增强）比 V5 差，同时改了 imgsz、mosaic、degrees、translate、erasing 五项，得不出任何可执行结论
- **根因**：多变量同改，效应无法分离；后续只能在错误结论上继续叠加实验
- **解法**：一次只动一个变量，其余从基线 `args.yaml` 逐项复制。**训练前用 diff 核对 args.yaml**，差异超过 1 项就不许开跑
- **证据**：`experiments/*/01_train/args.yaml` 横向对比
- **首次**：2026-10-21 · `V51_PREPROC_1021`

### L-009 用泛化间隙判断过拟合，不能跨增强配置比较
- **标签**：训练
- **现象**：曾用 `val/box_loss ÷ train/box_loss` 得出"V5 泛化最好（+5%）"，但 V5.1-A 是 +103%
- **根因**：**mosaic 会系统性抬高 train loss**，所以有 mosaic 的 run 天然显示更小的间隙，与泛化能力无关
- **解法**：只在**增强配置完全一致**的 run 之间比较间隙（如 V5 vs V5.2）；跨配置比较一律无效
- **证据**：`docs/v51_defense_qa_20261022.md` §2.2 第 3 条
- **首次**：2026-10-22

### L-010 参照物本身有病时，"把它修好"会被误读成"我的干预有效"
- **标签**：训练
- **现象**：曾得出"ROI 裁剪有效，mAP50-95 +0.0554"。真实原因是参照物 V5.1-A **严重过拟合**（val box loss 是 train 的 2.0 倍），ROI 只是把过拟合修回来了
- **根因**：对照组失效时，任何干预都"看起来有效"。而当时没有检查对照组的 train/val 关系
- **解法**：任何"干预有效"的结论，先验证**对照组本身健康**（train/val loss 关系、best epoch 位置、是否早停）。不健康的对照组只能用来做"修复"，不能用来做"归因"
- **证据**：`docs/v52_eval_report_20261022.md` §5.4 撤回记录
- **首次**：2026-10-21 → 2026-10-22 撤回

### L-011 增强模拟的必须是产线真实存在的自由度
- **标签**：训练
- **现象**：把 mosaic 1.0 / degrees 5.0 / translate 0.05 / erasing 0.4 全部加回，mAP50-95 反而 −0.0038
- **根因**：本产线是**固定工位、固定角度、无遮挡**。这些增强在模拟"不存在的拍摄变化"，学到的是产线上永远不会出现的分布
- **解法**：增强清单要先过一遍"产线有没有这个自由度"；没有的项不开，或只保留极低概率防止过拟合
- **证据**：`V51_ROI_1536` 与 `V52_ROI_1536_REG` 的单因素对比
- **首次**：2026-10-22

## 评测

### L-012 同一工作点算出两个不同的 FP，差值来自"图片怎么喂"
- **标签**：评测
- **现象**：V5.1-B 的 FP/千张 一份报告 127.2、另一份 125.7，对不上
- **根因**：`eval_report.py` 读 `.cache/eval_*_roi/images/*.jpg`（**q95 重编码过的 ROI 文件**），`sweep_workpoint.py` 是**在内存里从原图现裁**。同样 40 张图，两种喂法有 **24 张**的框不完全相同（±0.01 px 抖动，个别在阈值边缘翻转）
- **解法**：统一为**内存裁剪**（也更贴近产线：解码原图后直接切片，不落盘重编码）
- **证据**：修复后三份报告逐位一致（125.7 / 131.7 / 28.82%）
- **首次**：2026-10-22

### L-013 组级漏检的分母是"分组数"，不是"图片数"
- **标签**：评测
- **现象**：同一工作点出现 21.3% 与 28.2% 两个值
- **根因**：一张电芯有多张图，按图片算分母是 389，按电芯/批次分组去重后是 **170**。按图片算会系统性低估漏检
- **解法**：分母固定用 `group` 去重后的数量，`sweep_workpoint.py` 与 `eval_report.py` 共用同一实现
- **证据**：`reports/eval/*.json` 里 `n_defect_groups = 170`
- **首次**：2026-10-22

### L-014 `model.val` 的缩放口径与训练/推理不一致
- **标签**：评测
- **现象**：担心离线 mAP 系统性偏袒某个模型
- **根因**：`ultralytics/data/dataset.py:319`：`LetterBox(new_shape=(self.imgsz, self.imgsz), scaleup=False)`，**验证期不放大小图**；训练（`v8_transforms`）与推理（`predictor`）都是 `scaleup=True`
- **解法**：不改 site-packages（会破坏跨模型可比性）。用 `scripts/eval_scaleup.py` 做**对照实验**量化影响：V5 0.4186→0.4078（−0.0108）、V5.2 0.3977→0.3992（+0.0015），量级 ≤1.5σ，**排序不变**
- **证据**：`reports/eval/val_scaleup.json`
- **首次**：2026-10-22

### L-015 小样本子集的指标不要拿来下结论
- **标签**：评测
- **现象**：电芯级漏检"抽样 n=10 → 30%"，低分辨率组"71 张 → FP 翻倍"
- **根因**：n=10 时 ±1 颗就是 ±10pt；损伤在 test 只有 73 个框，±9 个就是 ±12pt
- **解法**：n < 100 的切片只做**方向参考**，写进报告时必须标 `n=`；结论只由 n ≥ 数百的整体指标支撑
- **证据**：`V52_ROI_1536_REG_v5test.json` 的 `cell_level_n: 10`
- **首次**：2026-10-22

### L-016 训练 `imgsz` 只能是方形 int
- **标签**：评测
- **现象**：传 `(1920, 1080)` 不报错，但实际按 `max()` 生效
- **根因**：`engine/trainer.py:340`、`engine/validator.py:141` 都调 `check_imgsz(..., max_dim=1)`；只有 `engine/predictor.py:274` 是 `min_dim=2`
- **解法**：训练/验证侧一律传单个 int，且 32 对齐；`core/preprocess.py:resolve_imgsz()` 已显式表达
- **证据**：`core/preprocess.py`
- **首次**：2026-10-21

### L-020 IoU 门槛必须先用标定表翻译成像素再定
- **标签**：评测
- **现象**：P0-1 预注册了「标注间 IoU 中位 >=0.75 通过」，做标定后才发现它要求两名标注员每边抖动 <=2px——而损伤框短边中位只有 17px，2px 就是 12%，对灰度雾状划痕近乎不可能达成
- **根因**：IoU 不是线性可比的量：同一 IoU 在不同尺寸、不同长宽比的目标上对应的像素误差差一个数量级。凭主观经验定门槛，会定出物理上做不到的数值，结果出来只能强行解释
- **解法**：定门槛前先做蒙特卡洛标定（真实框尺寸 + 已知抖动 sigma -> IoU 中位），把门槛反查成「每边允许几像素」再判断可行性。门槛一旦写定不事后改，但解读时必须引用标定表，并同时报中心点距离与尺寸比，把「没对准」和「边界画法不同」分开
- **证据**：标定：S 档 sigma 1/2/3/5px -> IoU 0.84/0.69/0.57/0.40；L 档 -> 0.87/0.76/0.67/0.51。故 0.75 对应 sigma 约 1.6~2.0px
- **首次**：2026-10-23


## 部署

### L-017 模型规格读不到时会静默按"全图"推，输出全废且不报错
- **标签**：部署
- **现象**：ROI 模型在 Web 端跑出来全是错框，但日志没有任何异常
- **根因**：`web/app.py` 的 `_load_model_spec()` 只在 `os.path.dirname(best.pt)`（即 `weights/`）下找 `_train_meta.json`，而该文件在 **run 根目录**（`weights/` 的上一层）。找不到就回退成默认 `{imgsz:1920, roi:False}` —— **把 16:9 全图喂给只在 647×991 上训练的模型**
- **解法**：同时查 `weights/` 与上一层；`_load_model_spec` 返回 `source` 字段，`source == 'default'` 时在页面上打黄标提示"该模型未登记规格"
- **证据**：`web/app.py`；5 个 run 的规格现已全部正确解析
- **首次**：2026-10-22

### L-018 ROI 模型上线必须带"裁剪有效性"检查
- **标签**：部署
- **现象**：若产线更换成像设备或改变拼图布局，固定归一化边界会把缺陷裁到画面外，模型照样输出"无缺陷"
- **根因**：ROI 边界是**硬编码常量**，不随成像布局自适应
- **解法**：推理前用 `core.roi.roi_looks_valid()`（灰度 std ≥ 20）做廉价自检；失败**必须报警转人工**，不允许静默当正常图
- **证据**：`core/roi.py`，4592 张全量标定（真实图 std ≥ 21.94，纯填充区 9.7~18.8）
- **首次**：2026-10-21
